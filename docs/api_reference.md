# CareGraph gRPC API Reference

The full schema is `proto/caregraph.proto` — this document is a guide to
that schema and to behavior that isn't obvious from the `.proto` file alone
(defaults, clamping, error codes). Where the two disagree, the `.proto`
file and `src/api/mod.rs` are the source of truth; this document should be
regenerated by hand whenever either changes.

Service: `caregraph.v1.CareGraphService`, one RPC per capability group
(PRD §2.4/§3.1, Layer 5).

## Authentication

Every RPC requires an `authorization: Bearer <token>` gRPC metadata entry,
checked by `AuthInterceptor` before any handler runs. `<token>` must match
the server's `CAREGRAPH_API_KEY` environment variable byte-for-byte. There
is no other auth scheme, no per-RPC scoping, and no token expiry — see
`src/api/mod.rs`'s module doc for why this is deliberately the smallest
real mechanism the PRD's one-line "auth" mention supports, not an
elaborate system invented beyond it. A missing or mismatched token returns
`UNAUTHENTICATED`.

The server refuses to start at all if `CAREGRAPH_API_KEY` is unset —
there is no way to run this API with authentication silently disabled.

## Result limits

`max_hops`, `max_result_nodes`, and `max_result_edges` (`TraversalLimits`,
`src/graph/limits.rs`) are enforced **server-side**, unconditionally. A
client's request fields only ever supply *values* the server clamps against
its own ceiling — a client cannot raise a limit past what the server
allows, only lower it. `TraverseResponse.effective_max_hops` reports the
hop count actually applied after clamping, which may be lower than what
`TraverseRequest.max_hops` asked for.

## RPCs

### `AddEdge(AddEdgeRequest) -> MutationResponse`

Writes a new edge version and, in the same atomic commit, recomputes every
embedding the mutation affects (Rule 5 — see `docs/patent_hooks.md` Claim
1). `model` selects which trained model computes the update; `GCN` is a
declared enum value with no trained weights anywhere in this deployment and
is rejected with `FAILED_PRECONDITION` rather than silently routed through
GraphSAGE's weights under GCN's name. Requesting a model that has no
`ml/deployed/<name>/model.pt` on this server also returns
`FAILED_PRECONDITION`. `edge_type = EDGE_TYPE_UNSPECIFIED` or
`model = MODEL_KIND_UNSPECIFIED` returns `INVALID_ARGUMENT`.
`properties_json` must be a valid JSON object string, or empty (treated as
`{}`); malformed JSON returns `INVALID_ARGUMENT`.

`MutationResponse.affected_nodes` lists every node the
`AffectedSubgraphResolver` recomputed an embedding for (PRD §4.1) — never
just the two edge endpoints. `fallback = true` means the incremental path
gave up and fell back to a full recompute for this mutation — logged and
counted (`incremental_fallback_total`, Rule 7), never silently absorbed
into `fallback = false`. `fanout_capped`/`neighbors_dropped` report whether
the resolver's own fan-out cap (512 neighbours per node, ring two only —
see `docs/benchmark_report.md` §7.7) bounded this mutation's receptive
field.

### `RemoveEdge(RemoveEdgeRequest) -> MutationResponse`

Same shape and same atomic-commit/fallback semantics as `AddEdge`, but
stages a tombstone version rather than deleting the key — the edge's
history before the removal stays queryable via `Snapshot`/`Traverse` at an
earlier `as_of_us` (see README's "Deletions are tombstones"). Any
`properties_json` on the underlying edge value is ignored for a removal.

### `Traverse(TraverseRequest) -> TraverseResponse`

Bounded, hop-limited, time-windowed graph traversal (PRD Phase 3,
`src/graph/traversal.rs`). `as_of_us = 0` reads the graph's very first
possible instant, not "now" — pass the current wall-clock microsecond
timestamp, or `u64::MAX` to mean "the latest version of everything," to get
current-state semantics. `direction` defaults to `DIRECTION_BOTH` for both
`DIRECTION_UNSPECIFIED` and an explicit `DIRECTION_BOTH`. An empty
`edge_types` list means "every edge type," not "no edge types." A
`window_from_us`/`window_to_us` pair of `(0, 0)` means "no window filter";
a non-zero pair restricts results to edge versions written inside that
window.

`TraverseResponse.truncation` reports whether the server's node/edge/
expansion ceilings were hit and (for the fan-out cap specifically) a lower
bound on how many neighbours were dropped — see
`TruncationMsg.fanout_dropped_neighbors`'s doc in the `.proto` file for why
that count can undercount but never overcounts.

### `Snapshot(SnapshotRequest) -> SnapshotResponse`

Full point-in-time reconstruction of one subject node and its live
relationships as of `as_of_us` (PRD Phase 3, `src/graph/snapshot.rs`).
`found = false` means the subject did not exist yet, or was retracted, at
or before `as_of_us` — `subject`/`related` are empty in that case, not a
zero-valued placeholder. An empty `edge_types` list means "every edge
type." A `related` entry's `node` field can be absent even when `found` is
true: a loader can write an edge before its target node's own first
version, and that dangling reference is surfaced as `node: None`, never
hidden or defaulted (see `RelatedEntityMsg`'s doc in the `.proto` file).

### `SimilarCarePathways(SimilarCarePathwaysRequest) -> SimilarCarePathwaysResponse`

Point-in-time embedding similarity search (Contribution 5,
`src/api/similarity.rs`) — reads the query node's `CF_EMBEDDINGS` entry as
of `as_of_us` and ranks every other node with an embedding at that same
timestamp by cosine similarity. `top_k = 0` defaults to 10, not zero
results. `query_node_has_no_embedding = true` means the node never went
through a mutation that computed one (or didn't exist yet at `as_of_us`) —
`matches` is empty in that case, which is a real, correct answer, not an
error. The query node itself is always excluded from `matches` — a
deliberate departure from the PRD's literal pseudocode (PRD §5.3), which
would otherwise trivially return the query node as its own top match at
similarity 1.0; see `similar_care_pathways`'s module doc.

## Enums

`EdgeType` and `ModelKind` discriminants (see `proto/caregraph.proto`)
mirror `src/types.rs`'s own numbering exactly and are load-bearing — never
renumber an existing value, only append new ones. `EDGE_TYPE_UNSPECIFIED`
and `MODEL_KIND_UNSPECIFIED` are both `0` and are always rejected as
`INVALID_ARGUMENT` rather than defaulted to some particular real value.

## Observability

`Traverse` and `Snapshot` both record into live Prometheus histograms
(`src/api/metrics.rs`, Phase 7): `traversal_latency_seconds` labeled by
`max_hops` (the *effective*, server-clamped value — a client's oversized
request never pollutes a different label's series with a latency it never
paid), and `point_in_time_query_seconds` for `Snapshot`. Both are served
at `GET /metrics` (`CAREGRAPH_METRICS_ADDR`, default `:9100`) alongside the
mutation-path metrics `src/embedding/metrics.rs` has recorded since Phase
4. See `observability/grafana/dashboards/caregraph_section1.json` for the
dashboard bound to these series.

## Example: end-to-end call sequence

`src/bin/demo_client.rs` (driven by `scripts/run_demo.sh`) is a working,
runnable example of all four RPCs called in sequence against a real
server: replay a real historical mutation live via `AddEdge`, `Traverse`
from the mutated patient, `Snapshot` that patient before and after the
mutation's timestamp, then `SimilarCarePathways` against the embeddings
the live mutations just produced. Read that file for exact request
construction, including the `authorization` metadata header every call
needs.
